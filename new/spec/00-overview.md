# ТЗ для Claude Code — сайт кондитерской Елены Абрикосовой (новый стек)

Это инженерное техническое задание разворачивает юридическое ТЗ из Приложения №1 к договору на разработку сайта (`Договор_на_разработку_сайта...docx`) в набор документов, достаточных для реализации проекта агентом Claude Code. Документ не описывает визуальный дизайн — дизайн-макеты (Figma) готовит отдельно приглашённый дизайнер на этапе 1 по договору; здесь зафиксирована только **структура** (данные, API, вайрфреймы, поведение).

## Как читать этот комплект документов

1. `analysis/ANALYSIS.md` — аудит текущей реализации сайта (Django), что забираем как основу, что переделываем.
2. `spec/01-data-model.md` — модель данных (SQLAlchemy) и seed-данные для разработки.
3. `spec/02-api-contract.md` — REST API контракт (FastAPI) между фронтендом и бэкендом.
4. `spec/03-pages-wireframes.md` — текстовые блок-схемы всех страниц сайта (mobile + desktop).
5. `wireframes/skeleton/*.html` — визуальные серые skeleton-вайрфреймы тех же страниц (открываются в браузере).
6. `spec/04-admin-panel.md` — спецификация админ-панели.
7. `spec/05-nonfunctional-and-acceptance.md` — безопасность, SEO, производительность, интеграции, что явно не входит в объём, критерии приёмки.
8. `spec/06-implementation-plan.md` — пошаговый план реализации для Claude Code (порядок задач).

## Цель проекта

Заменить текущий сайт-визитку (`abrikosova-elena.ru`, Django) на сайт-витрину с каталогом и корзиной на современном стеке, который: выглядит и работает современно на мобильном (приоритетное устройство), ведёт посетителя от просмотра каталога к оформлению заказа без регистрации, и управляется из понятной админ-панели без участия разработчика в повседневной работе.

Оплата на сайте не принимается — оплата при получении/по договорённости (сайт не является публичной офертой согласно тексту в футере текущего сайта, эта формулировка сохраняется).

## Технический стек (зафиксирован в договоре, Приложение №1, раздел 2)

**Frontend**
- Next.js 15, App Router, SSR + ISR (карточки товаров и каталог — ISR с ревалидацией; страницы контента — ISR; корзина/чекаут/админка — CSR/SSR без кэша)
- React 19, TypeScript (strict mode)
- Tailwind CSS 4
- shadcn/ui — база компонентов (кнопки, инпуты, модалки, таблицы для админки)
- Motion (бывш. Framer Motion) — интерфейсные анимации (переходы, hover, появление блоков)
- GSAP — сложные/интерактивные анимации (скролл-эффекты, галереи, если потребуются по дизайну)
- React Hook Form + Zod — все формы и их валидация (консультация, чекаут, отзыв, формы админки)

**Backend**
- Python 3.13, FastAPI
- SQLAlchemy 2.x (async), Alembic — миграции
- PostgreSQL — основная БД
- Redis — кэш (каталог/страницы); очередь фоновых задач опциональна (см. примечание ниже)
- JWT — авторизация в админ-панели

**Инфраструктура — хостинг Timeweb Cloud**

Хостинг закреплён за Timeweb Cloud (решение принято). Рекомендуемая раскладка сервисов — не самостоятельный хостинг БД/Redis в контейнерах на голом сервере, а управляемые сервисы провайдера, чтобы не тащить на себя админ-задачи (патчи, бэкапы уровня СУБД, отказоустойчивость), которые Claude Code как разработчику приложения решать не нужно:

- **Приложения** (`apps/web` и `apps/api`) — [App Platform / Cloud Apps](https://timeweb.cloud/docs/apps) — деплой из Git-репозитория (по Dockerfile или через buildpack), автоматический HTTPS-сертификат на выданном поддомене/подключённом домене, отдельные окружения (staging/prod) через отдельные приложения на одном аккаунте.
- **PostgreSQL** — [Managed Service for PostgreSQL](https://timeweb.cloud/services/postgresql) — управляемый инстанс вместо контейнера с Postgres на проде: автоматические бэкапы на уровне провайдера идут **в дополнение** к бэкапам из раздела «Резервные копии» админки (см. `04-admin-panel.md`), а не вместо них — админка всё равно должна уметь показать список копий и восстановить, это функциональное требование договора, а не просто инфраструктурная подстраховка.
- **Redis** — [Managed Service for Redis](https://timeweb.cloud/services/redis) — для кэша каталога/страниц и rate-limiting форм.
- **Хранилище изображений и файлов бэкапов** — [S3 Object Storage Timeweb Cloud](https://timeweb.cloud/docs/s3-storage), S3-совместимый API — данные физически хранятся на серверах в РФ, что закрывает требование 152-ФЗ о локализации персональных данных (см. текст `privacy_policy.html` в текущем сайте).
- **HTTPS** — обязателен на проде; на App Platform выпускается автоматически для домена приложения, дополнительной настройки Let's Encrypt/nginx вручную не требуется.

**Примечание про фоновые задачи (e-mail, бэкапы) без отдельного воркера.** Для масштаба этого проекта нет смысла держать отдельный деплой-юнит «воркер очереди» — это лишняя сущность на хостинге ради задачи, которая решается проще: отправка e-mail-уведомлений — через `FastAPI BackgroundTasks` прямо в процессе API-приложения (не блокирует ответ клиенту, отдельный воркер не нужен), плановые бэкапы — через встроенный в приложение планировщик (например, APScheduler) внутри того же процесса `apps/api`. Redis в этой схеме — только кэш и rate-limit, не очередь задач. Если нагрузка вырастет настолько, что это станет узким местом — тогда имеет смысл выносить в отдельный воркер (например, на `arq`) как отдельное приложение на том же App Platform; на старте это не требуется и не блокирует сдачу проекта.

## Структура репозитория (монорепо)

Админ-панель размещается **внутри того же Next.js-приложения** как защищённая route-группа `/admin` (решение принято осознанно: проект такого масштаба не оправдывает второе Next.js-приложение и второй деплой).

```
abrikosova/
├── apps/
│   ├── web/                    # Next.js 15 (App Router) — публичный сайт + /admin
│   │   ├── app/
│   │   │   ├── (public)/       # route group: главная, каталог, товар, о нас, контакты...
│   │   │   ├── admin/          # route group: защищённая JWT-мидлваром админка
│   │   │   └── api/            # опционально: BFF-роуты (проксирование/webhook), не бизнес-логика
│   │   ├── components/
│   │   ├── lib/
│   │   └── ...
│   └── api/                    # FastAPI-бэкенд
│       ├── app/
│       │   ├── models/         # SQLAlchemy-модели
│       │   ├── schemas/        # Pydantic-схемы
│       │   ├── routers/        # роутеры по доменам (catalog, cart, orders, reviews, gallery, admin, auth)
│       │   ├── services/       # бизнес-логика (заказы, уведомления, бэкапы)
│       │   └── core/           # конфиг, security, db-сессия
│       ├── alembic/
│       └── tests/
├── packages/
│   └── shared-types/           # (опционально) сгенерированные из OpenAPI TS-типы для web
└── docker-compose.yml          # postgres + redis + api + web для локальной разработки
```

Frontend и backend — два независимых деплой-юнита, связанных только HTTP API по контракту из `02-api-contract.md`. Это осознанное отличие от текущего Django-монолита, где шаблоны и бизнес-логика были в одном процессе.

`docker-compose.yml` с локальными `postgres`/`redis` — только для разработки на своей машине. На проде (Timeweb Cloud) эти два сервиса — управляемые (см. раздел «Инфраструктура» выше), `apps/web` и `apps/api` подключаются к ним по строке подключения из переменных окружения, без разницы в коде между локальным и продовым Postgres/Redis — меняется только `.env`.

## Принципы, которых должен придерживаться Claude Code при реализации

Эти принципы отвечают на проблемы, найденные в `analysis/ANALYSIS.md`, — они здесь не для галочки, а как прямое исправление конкретных найденных багов:

1. **Один источник правды для корзины.** Никакого дублирования состояния корзины в двух хранилищах одновременно (см. `ANALYSIS.md`, п. 2.1.3). Корзина живёт на бэкенде (гостевая сессия по httpOnly cookie с `cart_id`), фронтенд — тонкий клиент поверх API + React Query/SWR для кэша на клиенте.
2. **Секреты только через переменные окружения**, `.env` в `.gitignore` с первого коммита, `.env.example` без реальных значений в репозитории.
3. **Никакого дублирования кода между страницами** — переиспользуемые UI-блоки выносятся в компоненты (`components/ui`, `components/catalog`, ...), а не копируются между страницами, как было с инлайн-`<script>`/`<style>` в Django-шаблонах.
4. **Валидация и на клиенте (Zod), и на сервере (Pydantic)** — клиентская валидация не заменяет серверную.
5. **Все мутирующие эндпоинты — POST/PUT/PATCH/DELETE**, ни одного изменения состояния через GET (см. `ANALYSIS.md`, п. 2.1.4).
6. **Явное логирование ошибок** на бэкенде (structured logging), никаких голых `except: pass`.
