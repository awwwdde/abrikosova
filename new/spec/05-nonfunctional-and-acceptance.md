# Нефункциональные требования, интеграции, out-of-scope, критерии приёмки

## Безопасность (раздел 7 договора)

- **HTTPS обязателен** на проде (Let's Encrypt/сертификат хостинга) — без варианта работы по HTTP, в отличие от текущего dev-окружения Django с `DEBUG=True` и без настроенного `ALLOWED_HOSTS`.
- **Секреты** — только через переменные окружения (`.env`, не в git). Прямое следствие находки из `ANALYSIS.md` (п. 2.1.1–2.1.2): в старом проекте в открытом виде лежали `SECRET_KEY` и рабочие логин/пароль от прокси-сервера. В новом проекте: `.env.example` в репозитории без значений, реальные `.env` — только на сервере/в секрет-хранилище CI.
- **CSRF** — для cookie-based авторизации (админка) обязательна защита (двойной токен/`SameSite`); для JWT в заголовке `Authorization` классический CSRF неприменим, но refresh-токен в httpOnly cookie должен быть защищён `SameSite=Strict/Lax`.
- **XSS** — весь пользовательский ввод (отзывы, заявки, комментарии к заказу) экранируется на выводе; React по умолчанию экранирует, но при рендере `dangerouslySetInnerHTML` (если понадобится для форматированного контента страниц) — обязательная санитизация (например, DOMPurify).
- **SQL-инъекции** — SQLAlchemy ORM с параметризованными запросами, без ручной склейки SQL-строк.
- **Разграничение прав в админке** — см. матрицу ролей в `04-admin-panel.md`, проверяется не только в UI (скрытие пунктов меню), но и на бэкенде на уровне каждого admin-эндпоинта.
- **Защита форм от спама** — rate limiting через Redis на `/cart/items`, `/orders`, `/custom-cakes/consultation`, `/contacts/feedback` + honeypot-поле или капча (конкретный механизм — на усмотрение Claude Code на этапе реализации, требование — не давать боту засыпать формы).
- **Резервное копирование БД** — два независимых уровня, не заменяющих друг друга: (1) автоматические снапшоты на уровне [Timeweb Cloud Managed PostgreSQL](https://timeweb.cloud/services/postgresql) — включаются в настройках инстанса, работают без кода в приложении; (2) собственная функция бэкапа в админке (`04-admin-panel.md`, раздел «Резервные копии») — плановый дамп (`pg_dump`) по расписанию внутри `apps/api` (см. `00-overview.md`, примечание про фоновые задачи) плюс ручной запуск, файл дампа загружается в S3 Object Storage. Второй уровень обязателен, потому что раздел 5.7 договора требует именно управляемую **из админки** функцию бэкапа/восстановления, а не только инфраструктурный снапшот, невидимый заказчику.

## Хранение файлов

Хостинг — Timeweb Cloud (решение зафиксировано), поэтому вариант единственный, а не выбор на этапе деплоя: изображения товаров/галереи/тортов на заказ и файлы бэкапов хранятся в [S3 Object Storage Timeweb Cloud](https://timeweb.cloud/docs/s3-storage) (S3-совместимый API — на бэкенде используется стандартный S3-клиент, например `boto3`/`aioboto3`, без специфичного для провайдера SDK). Локальный `media/`-том на сервере API не используется даже для старта — на App Platform файловая система приложения не гарантированно постоянна между деплоями, а S3 сразу даёт устойчивое хранилище и решает вопрос локализации персональных данных по 152-ФЗ (данные физически в РФ, см. текст `privacy_policy.html` в текущем сайте).

Загруженные изображения товаров/галереи конвертируются в **WEBP** на бэкенде при сохранении (плюс сохраняется JPEG-фолбэк при необходимости) — раздел 2 договора требует WEBP/JPEG/PNG и «базовую оптимизацию скорости загрузки». На фронтенде — обязательно `next/image` с `sizes`/`srcset`, а не `<img>` напрямую, как было в старом коде.

## SEO и структурированные данные

- `generateMetadata` в App Router для title/description/OG-тегов на каждой странице (в старом коде мета-теги были только статичными в `base.html`, без учёта конкретной страницы/товара, кроме `product_detail.html`, где был отдельный JSON-LD блок — этот паттерн переносим на все типы страниц через `generateMetadata`).
- JSON-LD `schema.org/Bakery` на главной, `schema.org/Product` на карточке товара — переносится из старого кода как рабочее решение.
- `sitemap.xml` и `robots.txt` — генерируются автоматически (Next.js `app/sitemap.ts`, `app/robots.ts`), а не как статичный файл, который легко забыть обновить.
- Семантическая вёрстка, `alt`-теги на всех изображениях — обязательное требование раздела 2 договора.

## Аналитика и уведомления (раздел 6 договора)

- **Аналитика:** подключение Яндекс.Метрики и/или Google Analytics — счётчики подключаются через переменные окружения (ID счётчика), сам код — стандартный сниппет в `layout.tsx`.
- **Уведомления о заказах и заявках — на e-mail администратору** (основной обязательный канал по новому ТЗ, в отличие от старого кода, где был только Telegram через прокси с захардкоженными кредами — см. `ANALYSIS.md`, п. 2.1.10). Отправка e-mail — через `FastAPI BackgroundTasks` в процессе `apps/api` (см. `00-overview.md`, примечание про фоновые задачи), чтобы не блокировать ответ API на время похода к SMTP-провайдеру, без отдельного воркера.
- **Уведомление покупателю** — на экране (страница подтверждения заказа, см. `03-pages-wireframes.md`) обязательно; по e-mail — если у клиента есть e-mail (в текущей форме заказа поля email нет — по договору обязательно только имя/телефон, поэтому email-уведомление покупателю не гарантировано и не блокирует приёмку).
- **Telegram-уведомления** — по новому ТЗ это **опциональная надстройка, не обязательство подрядчика в рамках базового тарифа** (раздел 5.3 договора). Если её включать, то: токен бота и адрес прокси — только из переменных окружения, никаких значений в коде.

  **Прокси обязателен.** Проверено практикой: `api.telegram.org` из российских сетей не отвечает — TLS-соединение обрывается на рукопожатии (`SSL: UNEXPECTED_EOF_WHILE_READING`), что характерно для фильтрации по DPI. То же верно для Timeweb Cloud (подтверждено заказчиком на других его проектах, размещённых там же). Поэтому прокси в старом коде стоял не «из-за особенностей окружения разработчика», как предполагалось изначально, а по необходимости. Прокси — внешняя платная услуга и отдельная точка отказа, её оплата и сопровождение согласуются с заказчиком отдельно.

  Отправка выполняется фоновой задачей и **не влияет на оформление заказа**: если бот недоступен, заказ всё равно создаётся, а неудача пишется в лог с уровнем warning. В старом коде исключение проглатывалось в `print`, и недоставленное уведомление выглядело как успешный заказ, о котором никто не узнал (`ANALYSIS.md`, п. 2.1.10).

## Производительность

- ISR с ревалидацией для каталога/карточек товара (например, `revalidate: 300` секунд + point revalidation при изменении товара из админки через `revalidatePath`/`revalidateTag`) — баланс между актуальностью данных и нагрузкой на бэкенд.
- Redis-кэш на бэкенде для тяжёлых публичных выборок (список категорий, контент статичных страниц) — инвалидируется при изменении через админку.
- Ленивая загрузка изображений (`next/image` с `loading="lazy"` по умолчанию), как это уже частично было в старом коде (`loading="lazy"` на карточках).

## Явно не входит в объём (раздел 6 договора, «не входит в базовый тариф»)

Эти пункты фиксируются здесь явно, чтобы Claude Code **не реализовывал их по своей инициативе** — при обнаружении в процессе разработки, что что-то из списка «напрашивается», решение остаётся за заказчиком и оплачивается отдельно:

- Приём онлайн-оплаты на сайте (эквайринг, онлайн-касса) — оплата только «при получении/по договорённости».
- Интеграция с Telegram как обязательный канал (кнопка заказа через Telegram-бота, чат-бот) — в старом сайте была кнопка «Заказать десерт» через `t.me/konditerskaya_EA_bot`; в новом ТЗ такой кнопки в объёме нет, весь заказ идёт через каталог → корзину → чекаут на сайте.
- Виджет «Соберите свой торт» (конструктор торта).
- Подключение CRM и систем учёта.
- Интеграции со службами доставки (расчёт стоимости доставки, трекинг).
- Перенос контента из старой SQLite-базы (см. `01-data-model.md`, раздел Seed-данные — решение принято: только сид-данные).

## Критерии приёмки (раздел 8.3 договора, дополненные инженерными критериями)

1. Все 9 основных страниц + служебные (404, Политика конфиденциальности, Пользовательское соглашение, страница подтверждения заказа) открываются и корректно работают на мобильном, планшете и десктопе в основных браузерах.
2. Каталог и карточки товара корректно отображают все обязательные поля из раздела 4.2 договора, включая новые (порции, срок годности, условия хранения, метки).
3. Корзина и оформление заказа работают end-to-end: добавление товара → изменение количества → оформление → e-mail администратору → страница подтверждения.
4. Формы обратной связи и заявки на консультацию работают, обе сохраняют согласие на обработку персональных данных.
5. Админ-панель позволяет полностью управлять каталогом, заказами, заявками, отзывами, галереей и контентом статичных страниц без участия разработчика.
6. Резервное копирование БД работает — как автоматическое, так и ручное из админки.
7. HTTPS включён, секретов в репозитории нет (проверяется поиском по истории git перед публикацией, с учётом того, что в старом репозитории такая утечка уже была).
8. Сайт проходит базовую проверку производительности (Lighthouse/PageSpeed) без критичных предупреждений по изображениям и блокирующим ресурсам.
