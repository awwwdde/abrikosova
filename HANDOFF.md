## Резервные копии и очистка ПДн — сделаны

**Планировщик** (`core/scheduler.py`, APScheduler в процессе API): бэкап в 03:30, очистка ПДн
в 04:00 по Москве. Выключается переменной `SCHEDULER_ENABLED` — обязательно выключить, если
экземпляров приложения станет больше одного, иначе задачи запустятся в каждом.

**Бэкапы** (`services/backups.py`): `pg_dump -Fc` → выгрузка в S3, запись в `BackupRecord`.
Эндпоинты: список, ручное создание, восстановление, удаление — все только для роли `owner`.
Восстановление требует подтверждения словом `ВОССТАНОВИТЬ` и в теле запроса, и в интерфейсе.
`postgresql-client` добавлен в Dockerfile — без него `pg_dump` в контейнере недоступен.

**Очистка ПДн** (`services/retention.py`): завершённые и отменённые заказы старше
`PD_RETENTION_DAYS` обезличиваются (имя, телефон, комментарий, адрес), обработанные заявки
удаляются. Активные заказы не трогаются никогда. Строка заказа остаётся ради истории продаж.
Есть ручной запуск `POST /admin/retention/purge` — для демонстрации при приёмке.

### Три проблемы, найденные при проверке, и как решены

1. **Дамп базы был доступен анонимно.** Публичная политика бакета выдавалась на `/*`, то есть
   вместе с фотографиями наружу открывались `backups/` со всеми персональными данными клиентов.
   Теперь публичное чтение выдаётся только на префиксы изображений (`PUBLIC_PREFIXES` в
   `storage.py`). Проверено: дамп → 403, фото → 200.
2. **Восстановление зависало.** `pg_restore --clean` не мог получить блокировку, пока приложение
   держало соединения в пуле. Теперь перед восстановлением закрывается сессия, освобождается пул
   и разрываются остальные соединения через `pg_terminate_backend`. Это обрывает запросы,
   выполняющиеся в момент восстановления, — приемлемо для операции, которая и так затирает базу.
3. **История копий терялась после восстановления.** Запись о копии не была зафиксирована на момент
   снятия дампа и потому не попадала в снимок. Теперь запись и ключ коммитятся до `pg_dump`,
   а `reconcile()` при выдаче списка чинит статус `pending` по наличию файла в хранилище.

- Серверные компоненты ходят в API по внутреннему имени `http://api:8000`, браузер — по публичному
  порту. Это разные переменные: `API_URL` и `NEXT_PUBLIC_API_URL`.
- `apps/api/.env` указывает на `localhost:5433` — для запуска API вне докера (venv в `apps/api/.venv`).
- Docker Desktop иногда выключен; если команды `docker` падают на pipe — запустить его.
- `apps/web/node_modules` на хосте пустой (это том compose). Фронтенд-проверки —
  `docker compose exec web npm run typecheck` и т. п., либо `npm ci` на хосте.
